# 「一句话解释」词条撰写执行规则

> 用途：交给执行 AI，用于生成/改写 Code Atlas 文件树标注词典中约 200 条词条。本规则不是风格建议，是可直接执行的判定流程 + 写法规范。遇到规则没覆盖的新词条，按"判定流程"走一遍，不要凭感觉写。

---

## 〇、这句话存在的唯一理由

界面上每行已经有：图标 + 文件名 + **类型标签**（TS/JSON等）+ 子项数胶囊。

**这句话只允许提供"类型标签和文件名看不出来、但对新手有用"的信息。** 如果一条词条删掉之后，用户依然能通过文件名+类型标签获得同等信息，这条词条应该为空或极短，不允许硬凑句子。

写每一条之前，先问：**这条信息，新手不知道会不会吃亏，或者会不会一头雾水？** 答案决定它属于下面哪一档。

---

## 一、分档判定流程（写词条前必须先分档，不能跳过）

按顺序判断，命中即停：

```
1. 这个文件/文件夹的身份，类型标签+文件名已经说清楚了吗？
   是 → 归【档位1】，不写文字或只写极简范畴词
   否 → 下一步

2. 用错/动错它，会不会导致程序坏掉、密钥泄露、或者需要额外操作恢复？
   是 → 归【档位3】，必须写清楚"是什么 + 该怎么处理/不能做什么"
   否 → 下一步

3. 归【档位2】：只写"是什么"，不需要风险提示
```

状态类（未展开/空/锁定/截断）不走这个流程，见第五节单独规则。

---

## 二、档位1——纯类型兜底

**适用**：任意 `.ts` / 任意 `.md` / 任意 `.json` / 任意 `.png` 等靠后缀兜底、且类型标签已完整覆盖含义的情况。

**写法**：
- 默认**不写文字**，留空。
- 只有当后缀本身有二义性或行业黑话时，写 2–4 字的范畴词，不写完整句子。
  - 例：`.lock` 类文件（非 package-lock.json 精确匹配的其他 lock 文件）→ "锁文件"
- 陌生后缀（词典查无）→ 例外，必须写，因为这是"标签也答不上来"的唯一情况：
  - `🤔 未知类型，点击可问 AI`

**禁止**：不允许为了"看起来完整"而给档位1的条目编一句解释性文字（如"TypeScript 源代码：程序的一块积木"）。这类文字是噪音，删。

---

## 三、档位2——身份唯一、无风险

**适用**：文件/文件夹的功能值得说明，但用错/删掉不会造成实质损失（如 src、components、README.md、api）。

**写法规则**：

1. **直接说功能，不绕比喻。** 先写"正脸词"，读一遍——如果新手看正脸词已经懂了，就到此为止，不加比喻。
2. **黑话不能只翻译成另一个抽象词，要给具体例子。**
   - ❌ "业务逻辑：程序真正办事的代码"（"办事"仍是比喻，没有落地）
   - ✅ "处理具体业务功能的代码（比如下单、登录）" ——用真实场景例子替代抽象定义
3. **只有当正脸词本身对新手也是陌生词时，才允许配一个比喻**，且比喻只能描述"空间/容器"，**不允许把动作外包给虚构角色**（不写"体检医生""数据管家"这类人物拟人——这类比喻会让用户误以为有个"角色"在执行操作，而实际执行者是代码本身，这是认知错误，不只是风格问题）。
   - 允许：中间件 → "中间站：外部请求先经它检查一遍再往下走"（"中间站"是空间比喻，帮不熟悉这个词的人搭一个认知台阶）
   - 不允许：eslint → "代码体检医生"（人物拟人，动作主体错误）
4. **长度上限 14 字**，无风险提示需求，没有理由写更长。
5. 不重复类型标签/子项数胶囊已经显示的信息（不写"里面有xx个文件"）。

**示例**：

| 对象 | 写法 |
|---|---|
| src | 项目全部源代码 |
| components | 界面按钮、卡片等可复用小组件 |
| README.md | 项目说明：是什么、怎么运行 |
| services | 处理具体业务功能的代码（比如下单、登录） |
| api | 供其他程序调用的接口 |
| middleware | 中间站：外部请求先经它检查一遍 |
| styles | 界面的颜色、字体、间距样式 |

---

## 四、档位3——有风险/需要行动

**适用**：动错、删错、改错会导致程序损坏、机密泄露、或需要额外恢复操作的文件/文件夹（package-lock.json、.env、node_modules、dist、.gitignore 等）。

**写法规则**：

1. **公式固定为：是什么 + 该怎么处理**，两段都要有，行动提醒不能省。
2. **长度上限 20 字**（比档位2宽，因为行动提醒必须完整，不能因为字数砍掉"不要手改"这种关键尾巴）。
3. **同类风险用统一措辞，故意重复，不追求每条都换着花样写**。比如"自动生成的、不要手动改"这类文件（package-lock.json、node_modules、dist）都用「不要手动改」这个固定短语，不要为了"不重复"改成"别乱动""切勿修改"等变体——**用户看到同一句短语反复出现,会形成条件反射，这是产品在帮用户省心，属于故意的、有价值的重复**，跟档位1里被禁止的"信息量为零的重复"性质相反，两者不能用同一条降噪规则处理。
4. 涉及密钥/隐私的（.env）必须明确写出"不要外传/分享"，不能只写"重要"。

**示例**：

| 对象 | 写法 |
|---|---|
| package-lock.json | 锁定依赖版本，自动生成，不要手动改 |
| .env | 配置开关，常包含密钥，不要外传 |
| node_modules | 第三方库，删了能重装，不要手动改 |
| dist | 打包产物，不要手动改，改源代码后重新打包 |
| .gitignore | 告诉 Git 忽略哪些文件，不会被提交 |

---

## 五、状态类词条（空/锁定/截断/未展开）——独立规则，不套一至三档

状态类信息本质是"系统状态播报"，不是"这是什么东西"，调性应该**更接近日志，不用比喻、不用拟人**：

**公式：发生了什么 + （如果有）能怎么办**

| 状态 | 写法 |
|---|---|
| 未展开的大目录 | 还没展开，点击查看 |
| 系统锁定目录 | 系统保护目录，无法查看，不影响使用 |
| 空文件夹 | 空的，还没有内容 |
| 扫描被截断 | 文件太多，仅显示前 4000 个 |

**诚实底线（不可违反）**：
- 认不出的类型，必须明确说"未知"，不能编一个听起来合理但不确定的解释。
- 截断的数字必须加"仅显示前 N 个"或"至少"，不能给出看起来精确但实际不完整的数字。
- 不允许"完全不显示任何文字"来代替状态说明——空白本身会制造新的未知状态，比写错更糟。

---

## 六、语言与腔调硬性规则

1. **不用人格化口语词**：咱、啥、师傅、瞧、搞、玩意儿——一律不用。判断标准：这句话读起来应该像"同事在工位上跟你说的一句话"，不能像"一个虚构角色在讲故事"。
2. **黑话处理**：出现"业务逻辑""依赖""中间件""打包"等术语时，优先用具体例子替代抽象翻译（见第三节规则2）；如果确实没有更简单的说法，术语可以保留，但下半句必须立刻给出等价的具体解释。
3. **术语一致性**：以下词的用法全篇统一，不混用：
   - "什么"（不用"啥"）
   - "扫描"（不用"探"）
   - "手动改"（不用"手改""瞎改"）
4. **不写"都在这里""就在这"这类位置性废话**——文字本身已经出现在该文件/文件夹旁边，这类话是废字。
5. **每条词条只服务于自己的档位长度上限**（档位1不写或极短，档位2 ≤14字，档位3 ≤20字），超过上限先删形容词，再删修饰，最后才考虑分两行。

---

## 七、生成/改写时的自检清单（每条词条过一遍）

- [ ] 先分档：这条属于档位1/2/3，还是状态类？
- [ ] 遮住冒号前的比喻/标题词，剩下的字能不能单独回答"这是什么/该怎么处理"？不能 = 重写。
- [ ] 有没有用了人物拟人比喻（体检医生、数据管家类）？有 = 换成空间比喻或直接删掉比喻。
- [ ] 有没有把黑话直接留在原地没解释，或只翻译成另一个抽象词？有 = 补具体例子。
- [ ] 长度是否超过本档上限？超 = 先砍形容词/修饰语，不砍行动尾巴。
- [ ] 是否重复了类型标签/子项数胶囊已经显示的信息？有 = 删。
- [ ] 同层级的兄弟词条（如 src/vendor/services/store 这类并列目录）是否使用了同样的信息密度和句式结构？不一致 = 拉平重写，不能有的认真写有的随手写。

---

## 八、重复渲染处理（同目录内同句多次出现时）

- 从第二次起，**只显示 emoji，隐藏文字，鼠标悬停显示完整文字**。
- 例外：档位3（风险类）的重复是刻意设计的记忆强化，**不适用本条降噪规则**，风险类词条即便重复出现也保留完整文字，不做隐藏处理。
- 如果某条兜底规则（如"任意.ts"）在实际使用中频繁触发重复，说明这条规则本身信息密度不足，应该按第二节规则改成"默认不写文字"，而不是靠渲染层降噪掩盖。
