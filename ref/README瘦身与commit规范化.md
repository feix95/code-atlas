# README 瘦身 + Git 提交规范化

> 给执行侧 AI 直接开工用。这是流程/文档类改动,不涉及功能代码,但同样遵守"一次只做一件事、改完自测(至少跑一遍 build 确认没弄坏东西)再提交"的规矩。

---

## 模块一:README 瘦身,开发日志搬家

### 现状问题

`README.md` 的"## 进度"部分把从第一锤到现在的每一条都完整堆在里面,已经 30 多行,而且会随着开发一直无限增长下去。README 本来该是"这是什么项目、怎么装、怎么跑"的门面,不该变成一份逐条流水账。

### 要求

1. 新建 `CHANGELOG.md`,把现有 README 里"## 进度"清单**原样完整**搬过去(不要精简、不要重写措辞,这是真实开发记录,照抄过去就行),按现在的顺序(从第一锤到最新)保留。
2. `README.md` 的"## 进度"部分替换成一段简短的"当前支持的核心功能"总结(3~8 条 bullet,面向"这个 App 能干什么",不是"开发过程中做了哪几件事"这个视角),末尾加一句"完整开发历程见 [CHANGELOG.md](./CHANGELOG.md)"。
3. 以后每次完成一锤,**新增记录写进 `CHANGELOG.md`,不要再写回 README**。

---

## 模块二:Git 提交信息改用 Conventional Commits 规范

### 现状问题

现在的提交信息格式是"第 XX 锤:大白话说明",信息量足但不是行业通用格式,外部协作者/工具不好识别。另外发现 `4183aa4`("第二十三~二十九锤")和 `4ec6685`("第三十~三十二锤")这两条提交**一次性塞了好几个模块**,违反了自己 `CLAUDE.md` 里"一次只开发一个模块"的规矩——这个不用回头改(历史提交不用重写,公开仓库改历史没必要),**但以后不能再这样,一锤对应一个 commit,不许合并打包提交**。

### 要求

1. **从下一次提交开始**,commit message 格式改成:

   ```
   <类型>(<影响范围>): <一句话说清楚改了什么,延续现在的大白话风格>
   ```

   类型固定从这几个里选:`feat`(新功能)、`fix`(修 bug)、`docs`(只改文档)、`refactor`(代码整理不改行为)、`chore`(杂活:依赖/配置/构建脚本)、`perf`(性能优化)。

   影响范围(scope)填改动集中在哪个模块,比如 `scanner`、`window`、`ai`、`appearance`、`readme` 等,自己按实际改的模块起名,不用死抠一个固定列表。

2. **不要重写过去的提交历史**——已经推上去的 commit 保持原样不动,只对以后新提交生效。

3. **"第几锤"这个编号不用写进 git commit message 里了**,改记录进 `CHANGELOG.md`(模块一新建的那个文件)——这样一次改动会同时留两笔记录:git log 里是规范化的一行,`CHANGELOG.md` 里是延续原来"第 XX 锤:详细大白话说明"的完整版本,两边不重复也不矛盾。

4. 以后**严格一锤一个 commit**,不许像之前那样一条提交塞好几个模块。

### 举例(改动前后对比)

改之前:
```
第十八锤:地址栏 —— 路径直接输,回车就开图
```

改之后,git commit message 变成:
```
feat(address-bar): 路径直接输,回车就开图
```

同时 `CHANGELOG.md` 里对应新增一行:
```
- [x] 第十八锤:地址栏(路径直接输,回车就开图)
```

## 验收标准

1. `CHANGELOG.md` 存在,内容是搬过去的完整历史清单;`README.md` 的"进度"部分变成简短功能总结 + 指向 CHANGELOG 的链接。
2. 下一次新提交的 commit message 符合 `<类型>(<范围>): <说明>` 格式。
3. 确认这次改动本身也遵守"一次一个模块",别顺手把 README 改动和别的功能改动混在一个 commit 里提交。
