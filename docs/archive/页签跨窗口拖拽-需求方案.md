# 页签跨窗口拖拽 · 需求方案

状态: 已完成(2026-10-21), 归档记录; 跨窗正文只追加不拆半屏, 边界见交接文档「页签跨窗拖拽」
日期: 2026-10-21
范围: 主窗与子窗之间、子窗与子窗之间的页签拖动; 子窗多页签与分屏
依据: 现有页签模型、页签独立窗口实现、交接文档「产品与验收契约」页签条

## 1. 一句话定位

把现在「只能从主窗单向拆出一个子窗」升级为 Chrome / Edge 式跨窗页签: 主窗与任意子窗之间、子窗与子窗之间可以拖动页签合并、按位置插入、拖回主窗; 子窗可以承载多张页签, 并继续沿用左右两组分屏。

### 2.2 卡点

| 卡点               | 具体表现                                                             | 根因                                                                   |
| ------------------ | -------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 子窗不能叠加多张签 | 每次拆签都 `openAuxWindow()` 开新窗, 没有「放进已有子窗」的落点      | `detachTabToWindow` 只会开新窗; 拖拽引擎只认本窗                       |
| 子窗之间不能互拖   | 拖到子窗上仍被判定为「窗外」, 松手又开一扇新窗                       | `TopBarTabs` 的几何快照只查 `el.ownerDocument` 一扇窗                  |
| 子窗签不能拖回主窗 | 同上; 而且主窗拖空后没有页签带, 没有可瞄准的条带                     | 引擎没有跨窗命中; 主窗零组时不渲染 `TopBarTabs`                        |
| 跨窗没有落点反馈   | 拖拽芯片和插入线都只画在来源窗; 指针进入别的窗时视觉上「什么都没有」 | 芯片是来源窗的 `position: fixed` 浮层, 插入线是目标窗自己的 React 状态 |

### 2.3 现有实现里可复用的资产

- `moveTabToHost` 已经处理了跨 host 搬签、源组消亡、激活指针接力, 本次只需补「插到第几位」。
- `dropMark` 已经是全应用共享状态, 跨窗正文边缘提示几乎不用新增状态。
- `groupsForHost` / `groupHost` / `dropHostGroups` 已经是跨窗登记的唯一口径。
- `TabBar` 的 `gapIndex` 已经能画插入线, 只差把落点喂给它。
- `auxWindows.ts` 已经有 `frameName` 白名单和 BrowserWindow 注册表, 但渲染层目前只需要窗口对象本身, 不一定要新增 IPC。

| 1. 主窗可以拖出子窗     | 已有                                     | 保持; 拖到空白处仍然拆新窗         |

| 1. 子窗支持分屏         | 有壳, 但子窗通常只有一张签, 拆不出第二组 | 多页签进来后自然可用; 补验收       |

## 4. 方案

### 4.1 核心思路

不重写拖拽引擎, 不动页签数据模型, 不引入新依赖。只在现有 pointer 引擎外面加一层「跨窗识别」:

1. 拖拽开始时, 把当前所有窗口的页签带和正文位置量一次, 按窗口登记成快照。
2. 指针在来源窗内, 走现有逻辑, 一行不改。
3. 指针出了来源窗, 用屏幕坐标判断落在哪扇窗, 换算成那扇窗的局部坐标, 再套用同一套条带 / 正文判定。
4. 落点反馈: 插入线和拖拽芯片用 React Portal 画进目标窗的 document, 外观复用现有插入线和胶囊样式。
5. 松手: 目标窗不是来源窗时, 走扩展后的纯函数落账; 目标窗是来源窗时, 走现有逻辑。

选择这条路的原因: 跨窗换账、按窗渲染、关窗清账这三件事现有代码已经做对了; 缺的只是「指针现在在哪扇窗」和「插到第几位」。重写引擎或改走原生 HTML5 拖放, 会丢掉现有活序滑动、胶囊形变和磁性带手感, 改动面反而更大。

### 4.2 交互规则

| 动作                                 | 反馈                               | 结果                                             |
| ------------------------------------ | ---------------------------------- | ------------------------------------------------ |
| 来源窗内本组条带拖动                 | 现有活序滑动, 邻居让位             | 同组重排                                         |
| 来源窗内另一组条带                   | 目标条带画插入线                   | 挪到另一组指定位置                               |
| 拖到另一扇窗的页签带                 | 目标窗条带画插入线, 芯片跟到目标窗 | 插入该组指定位置, 点亮该签                       |
| 拖到另一扇窗的正文                   | 目标窗正文亮边提示                 | 追加到该组末尾; 边缘三分之一是否拆半屏见待确认项 |
| 拖到主窗但主窗零组                   | 主窗正文亮边提示                   | 在主窗现立一组并放入                             |
| 拖到所有窗口之外                     | 芯片挂拆窗预告样式                 | 开一扇新子窗                                     |
| 拖回来源窗                           | 现有逻辑                           | 不动作或同窗重排                                 |
| 拖拽中按 Esc / 窗口失焦 / 目标窗被关 | 取消, 芯片飞回                     | 状态表不动                                       |

### 4.3 技术实现

#### 4.3.1 窗口清单与几何快照

- 新增一个窗口清单, 由 App 组装: 主窗 `{ host: 'main', win: window }` 加每扇子窗 `{ host: aux.id, win: aux.win }`。
- 通过 `tabArea` 传给主窗和各子窗的 `TopBarTabs`, 同时补一个 `host` prop, 让引擎知道自己在哪扇窗。
- 拖拽开始时, 对清单里每扇未关闭、未最小化的窗各量一次:
  - 窗口屏幕原点与内容尺寸: `win.screenX` / `win.screenY` / `win.innerWidth` / `win.innerHeight`。
  - 各条带: `.topbar-strip` 的局部矩形、`.tabbar` 左缘、每张签的左缘 / 中线 / 右缘。
  - 各正文: `.pane-body` 的局部矩形与 `data-group-id`。
  - 零组窗口的兜底落点: 主窗 `.detail` 或 `.pane-groups` 的矩形, 组 id 记空。
- 给 `.topbar-strip` 补 `data-group-id`, 不再靠数组下标猜组 id。
- 快照只量一次, 与现有做法一致; 拖动期间窗口一般不动, 不逐帧回读 DOM。

#### 4.3.2 跨窗命中

- 指针在来源窗内: 现有 `clientX / clientY` 逻辑不变。
- 指针出了来源窗:
  - 用 `pointermove` 的 `screenX / screenY` 找包含该点的窗口。命中顺序: 来源窗优先, 其次子窗按打开顺序倒序, 主窗最后。重叠窗口的层级是已知近似, 见风险表。
  - 换算成目标窗局部坐标后, 先判页签带 (沿用 `isWithinStripBand` 和 32px 磁性带), 再判正文, 都没有则算「窗外」。
  - 插入位置沿用 `dragCenterX` + `insertIndexAt`, 输入换成目标窗局部坐标和目标条带快照。
- 判定函数抽成纯函数放新文件, 便于自测:
  - `snapshotDragWindows(refs)`: 量几何, 碰 DOM。
  - `windowAtPoint(snaps, screenX, screenY)`: 找目标窗并换算局部坐标。
  - `locateGap(strip, localX, grabDx, chipW)`: 算插入序号。
  - `gapLeftAt(mids, barLeft, index)`: 算插入线的横坐标, 与芯片沉降共用。

#### 4.3.3 反馈

- 拖拽芯片: 目标窗不是来源窗时, 用 `createPortal` 把现有芯片画进目标窗 `document.body`, 坐标用目标窗局部坐标; 指针不在任何窗口时保持现状 (芯片在窗外不可见, 松手拆新窗)。
- 插入线: 目标窗不是来源窗时, 同样 Portal 一条 fixed 竖线到目标窗 body, x 用 `gapLeftAt`, y 用条带快照。颜色沿用现有插入线的 `--drop-mark` (由 `--sash-hi` 混出), 不另起蓝色。
- 正文边缘: 复用全局 `dropMark`, 目标窗的 `PaneGroups` 会自动亮提示, 不需要新增状态。
- 所有 Portal 浮层 `pointer-events: none`, 不挡落点判定。
- 目标窗关闭或 document 失联时, 本帧不画浮层并取消该目标。

#### 4.3.4 落账

扩展现有纯函数, 不另起一套:

```ts
// 目标组由 groupId 指定; atIndex 为 null = 追加到末尾
moveTabToGroupAt(
  groups: PaneGroup[],
  tabId: string,
  targetGroupId: string | null,
  host: string,
  atIndex: number | null
): { groups: PaneGroup[]; activeGroupId: string } | null
```

规则:

- 目标组存在: 插到 `atIndex`, 点亮被拖签。
- 目标组为空 (`targetGroupId` 为 null): 找该 host 第一张非空组; 一个都没有就现立一组, host 记为 `host`。
- 源组搬空: 删组, 与现有 `moveTabToHost` 一致。
- 同组内插: 先摘后插, 按目标序号修正偏移。
- `moveTabToHost` 改为委托这个函数, 保持现有签名和自测不变。

`usePaneTabs` 暴露 `moveTabToHostAt`, 内部调用纯函数 + 设激活组 + 树里照过来。

松手分流:

| 落点           | 调用                                        |
| -------------- | ------------------------------------------- |
| 来源窗条带     | 现有 `moveTab`                              |
| 来源窗正文边缘 | 现有 `moveTab(..., 'sibling', ...)`         |
| 其他窗条带     | `moveTabToHostAt(id, host, groupId, index)` |
| 其他窗正文     | `moveTabToHostAt(id, host, groupId, null)`  |
| 所有窗外       | 现有 `onTabDragEnd` 拆新窗                  |

#### 4.3.5 空窗与关窗

- 子窗被拖空: 现有壳层自裁逻辑继续生效, 窗口关闭后 `closeHostGroups` 清账。本次不新增关窗路径。
- 主窗被拖空: 保持空板; 拖回时用正文兜底落点现立一组, 解决「主窗没有条带可瞄准」的死胡同。
- 会话存档: 继续不记 `host`, 重启后子窗的签回主窗。与现有口径一致, 本次不改。

### 4.4 待确认项

| 编号 | 问题                                                       | 哥的建议                                                                                            |
| ---- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| D1   | 拖到另一扇窗的正文中间, 是「追加到该组末尾」还是「不动作」 | 追加。Chrome 也是落在内容区就并入该窗; 只在来源窗内维持「正文不接收页签」的老规矩, 避免改坏现有手感 |
| D2   | 拖到另一扇窗正文左右三分之一, 要不要拆半屏                 | 第一阶段不做, 先保证合并和拖回; 第二阶段若目标窗只有一组再补拆半屏                                  |
| D3   | 拖进另一扇窗后, 要不要把目标窗带到前台                     | 建议带前台 (Chrome 同款); 实现只需现有 `auxWindowOp(host, 'focus')`                                 |
| D4   | 子窗多页签后, 右键菜单是否补「移到窗口」子菜单             | 本次不加, 只做拖拽; 菜单项越多越难维护, 等拖拽稳定后再看                                            |

### 4.5 明确不做

- 不做整组拖动 (一次只搬一张签)。
- 不做页签组、固定签、悬停预览卡。
- 不把子窗布局写进会话存档。
- 不改用原生 HTML5 拖放, 不引入第三方拖拽库。
- 不做跨应用拖拽 (拖到别的软件或桌面文件)。
- 不做桌面上的常驻拖拽幽灵窗; 指针在所有窗口之外时芯片不可见, 这是现有行为。
- 不保证重叠窗口的完美层级判定; 见风险表。

## 7. 风险与兜底

| 编号 | 风险                                                | 可能性 | 影响                         | 兜底                                                                                                                                                                       |
| ---- | --------------------------------------------------- | ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| R3   | 子窗重叠时无法得知真实层级                          | 高     | 可能落进被遮住的窗           | 命中顺序按来源窗优先、子窗打开顺序倒序; 记为已知限制, 不追求完美                                                                                                           |
| R4   | 跨窗换 Portal 锚点会重建正文 DOM                    | 高     | 滚动位、编辑器局部状态可能丢 | 实测聊天 / 音频 / 设置等关键状态; 丢的部分记入已知取舍, 本次不做跨窗 keep-alive                                                                                            |
| R5   | 拖拽期间目标窗被移动、缩放或关闭                    | 低     | 快照过期, 落点偏             | 目标窗 `closed` / `document.hidden` 时跳过; 松手前再校验目标组仍存在                                                                                                       |
| R6   | 子窗没有 preload, 新浮层样式在旧子窗里缺失          | 低     | 插入线或芯片样式不对         | 浮层只用现有已克隆的类与 token; dev 下新开子窗验证                                                                                                                         |
| R7   | 主窗零组时没有页签带                                | 确定   | 拖回主窗无处可落             | 正文兜底落点 + 现立一组, 纳入 A5                                                                                                                                           |

Plan B 的代价: 主进程新增一个拖动会话与若干 IPC, 预计多半天到一天; 好处是不依赖跨原生窗的 pointer 事件, 是更稳的长期方案。M0 结论出来后再决定是否直接走 B。

## 9. 测试计划

- 纯函数自测: 跨组插入、队尾追加、同组插序偏移、源组搬空、目标组不存在、空 host 现立组; 屏幕坐标命中与局部坐标换算; 插入线 x 落点。
- 现有自测: `test:panehost` 与 `test:tabdrag` 必须零回归。
- 手工矩阵: A1 到 A12; 至少覆盖主窗到子窗、子窗到子窗、子窗到主窗、主窗零组、所有窗外五种落点。
- 缩放与双屏: 100% / 125% / 150% 至少两档; 双屏记录一次。
- 全链: `npm run typecheck` → `npm run lint` → `npm test` → `npm run build` → `npm run test:journey`。
- 视觉验收交给小葵: 插入线、芯片、目标窗提示的实际观感; 数值推算不能替代肉眼确认。

## 10. 已知取舍

- 子窗布局不持久化, 重启后回主窗, 沿用现状。
- 重叠子窗的层级判定用近似顺序, 不保证永远命中肉眼最上面的那扇。
- 跨窗换 Portal 锚点可能重建正文 DOM, 滚动位等局部状态不保证保留; 关键业务状态由现有全局 store 承担。
- 指针在所有窗口之外时, 拖拽芯片不可见, 只有松手拆新窗的动作; 不做桌面级幽灵窗。
- 正文边缘跨窗拆半屏放到第二阶段, 首版只保证合并、插入和拖回。
