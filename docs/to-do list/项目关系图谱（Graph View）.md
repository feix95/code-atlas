### 一、项目关系图谱（Graph View）需求表

**功能名称**：项目关系图谱（Graph View）

**目标**：  
把现有「项目关系分析」（depgraph）从列表/排行升级为可交互的力导向图谱，让用户一眼看清整个项目的文件/文件夹依赖结构，风格参考 Obsidian Graph View。

**核心需求**：

1. **节点范围**
   - 显示项目内所有文件夹和文件（以扫描结果为准）。
   - 支持孤立节点（没有任何引用关系的文件，如 README、LICENSE、部分配置文件），以独立圆球形式出现在图中，不强制连线。

2. **边（关系）**
   - 使用现有 depgraph 计算出的引用/依赖关系作为连线。
   - 有向边优先（谁引用谁），可视化上可区分方向。

3. **节点标注**
   - 对节点进行语义标注，至少支持以下类型（可用小图标 + 文字标签）：
     - 入口（entry）
     - 配置（config）
     - 测试（test）
     - 核心模块（被引用次数高）
     - 文档（README 等）
     - 普通文件
   - 标注规则先用启发式（文件名、路径、被引用次数），后续可扩展为用户手动标注。

4. **交互与布局**
   - 力导向布局，支持缩放、拖拽、平移。
   - 点击节点可跳转到对应文件预览 / AI 讲解。
   - 支持按类型过滤、搜索高亮。

5. **懒加载（必须）**
   - 默认不一次性加载全部节点。
   - 首屏策略建议：
     - 优先显示有引用关系的节点 + 入口文件 + 被引用次数靠前的节点。
     - 目录默认折叠为聚合节点，点击后再展开子文件。
     - 孤立节点默认收纳在「未连接」分组，用户主动展开后才散开。
   - 与现有扫描器的节点预算 / lazy 机制保持一致思路。

6. **技术约束**
   - 基于现有 Electron + React + TypeScript 栈。
   - 优先复用现有 depgraph 数据，不重新发明关系计算。
   - 图谱为「关系分析」的可视化升级，而非独立平行功能。
   - 大项目性能必须可控（参考现有 4000 节点预算思路）。

7. **非目标（当前阶段不做）**
   - 不做 3D 图谱。
   - 不做实时协作编辑关系。
   - 不做自动重构建议。
